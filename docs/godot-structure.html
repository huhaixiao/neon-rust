目录结构与扩展性：现状 vs 建议

neon-rust · Godot 4.7.2 · 11 个 .gd / 1,388 行
结论：现在的目录本身不算错，问题在于“按文件类型分 + 单脚本装下多种敌人 + Game 当节点仓库”这三件事让加内容变贵。目录可以按功能重排，但真正决定扩展性的是数据和通信方式。
现状：按文件类型分（flat）
加一个敌人要动 3 个文件、且都在不同目录
scenes/ 6 个 .tscn 全平铺 ├ main.tscn ├ player.tscn ├ enemy.tscn └ 三种敌人靠 enum 分支 ├ bullet.tscn ├ pickup.tscn └ hud.tscn scripts/ 11 个 .gd 全平铺 + .uid ├ game_state.gd └ 还存 6 个节点引用 ├ input_setup.gd ├ fx.gd ├ player.gd ├ enemy.gd └ CHASER/BRUTE/SPITTER ├ bullet.gd ├ pickup.gd ├ spawner.gd ├ camera_rig.gd ├ hud.gd └ main.gd assets/ sprites + sounds 两层堆一起 data/ 不存在（0 个 .tres） shaders/ 空目录
建议：按功能分（feature-first）
一个功能的场景 / 脚本 / 数据放在同一棵树里
core/ 全局层，只有常驻逻辑 ├ events.gd 事件总线（替代节点引用） ├ game_state.gd 分数/波次/存档 └ input_setup.gd entities/ ├ player/ player.tscn · player.gd │ player_stats.tres 数值进数据 ├ enemies/ enemy_base.gd │ chaser.tscn/gd brute.tscn/gd │ spitter.tscn/gd ├ bullets/ bullet.tscn · bullet.gd └ pickups/ pickup.tscn · pickup.gd systems/ ├ waves/ spawner.gd · waves.tres ├ fx/ fx.gd · burst.tscn └ camera/ camera_rig.gd ui/ ├ hud/ hud.tscn · hud.gd · theme.tres └ debug/ debug_overlay.tscn data/ 纯资源，无脚本 ├ enemies/ chaser.tres brute.tres spitter.tres └ drops/ drop_table.tres assets/ sprites/ · audio/ · fonts/ addons/ 第三方插件（不手改） world/ main.tscn · arena.tscn

四个真正拖扩展性的点

现状 为什么会疼 怎么改
enemy.gd 一个脚本三种敌人 加第四种敌人 = 改 if/elif、改 spawner 的权重表、改 hp_ramp 分支，三处联动，还容易漏 抽 enemy_base.gd + 每种敌人一个 .tscn，数值放 EnemyDef.tres，spawner 只读数据表
Game 里存 player / bullets_root / spawner / camera 任何一个节点改路径或换场景，全局报错；Game 变成隐式全局变量袋，单测也难跑 节点自注册到 groups（"player" / "bullets"），需要时 get_tree().get_first_node_in_group()；跨系统事件走 events.gd 信号
没有任何 .tres 数据资源 波次、掉落率、敌人属性全是魔法数字写在代码里，策划/调平衡要改代码 @export var def: EnemyDef 配合 Resource 子类，平衡表变成 data/ 下可 diff 的文本
scenes/ 与 scripts/ 分家 改 player 要在两个目录来回跳；删除/移动时 .tscn 的 ext_resource 路径容易断，.uid 也要跟着搬 同功能同目录、同名同放：entities/player/player.tscn + player.gd，用编辑器移动会自动修引用

迁移顺序（低风险，四步）

1 · 先搬目录，不动逻辑　用 Godot 编辑器里的 FileSystem 面板拖动（不要用 shell mv），.tscn 的 ext_resource 与 .uid 会自动重写；搬完跑一遍 smoke + pause 测试。
2 · 再拆敌人　enemy_base.gd 收敛公共逻辑（追击、受击、死亡掉落），三种敌人各自一个场景继承；spawner 改成读 waves.tres。
3 · 最后解耦 Game　节点改为加入 group，Game 只留分数/波次/存档和信号；这一步才需要动 main.gd 的装配代码。
4 · 收尾　补 addons/ 与 data/，更新 export_presets.cfg 的 exclude_filter（新增目录若不该进包要排除），重新出 Deck 包。
反方向的提醒：1,388 行的项目不需要上 ECS、不需要每个实体都做插件化。目录重排的收益远小于上面三条（数据化、去节点引用、拆敌人类型）——先做这三件，目录顺手就顺了。
现状核对：scenes 6 个 .tscn、scripts 11 个 .gd 全部平铺；仓库内 0 个 .tres；game_state.gd 持有 player / bullets_root / enemies_root / pickups_root / fx_root / spawner / camera 引用。
